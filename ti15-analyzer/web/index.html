产品理解稿 · 不是赛评本身

先把「看什么、数据从哪来、怎么算、怎么部署」钉死，再写每场分析。

你要的不是一篇 Cursor 里的长评，而是一个能反复打开的网页：TI15 淘汰赛每场对决、历史交手、常用英雄、赛前 BP 模拟、赛况推演，最后落到可执行的竞猜参考。 下面是我对这件事的判断，以及现在真正能接到的数据接口。

赛事The International 2026（TI15）

1. 我的看法

这件事值不值得做成站

值。TI 淘汰赛窗口只有四天，信息密度极高：队名改了、瑞士赛刚打完、BP 会按对手变、Bo3/Bo5 的盘口逻辑完全不同。靠每次打开 Cursor 问一遍，时效和对齐成本都太高。做成站的核心价值是同一套数据 + 同一套模型，赛程更新后刷新，而不是重写文章。

不要做成第二个液体百科

Liquipedia 已经把赛程、阵容、比分、英雄统计做得很好。我们不该再做一个百科。差异化在后半段：交手画像 → 英雄池/禁用倾向 → 模拟 BP → 系列胜率 → 竞猜决策。百科给事实，我们给「这场该怎么下判断」。

竞猜模块必须克制

分析可以指导预测，但不能做成投注站。产品输出应是：系列胜率、最可能地图分、信心区间、以及「不该追的盘」。不爬非法博彩盘口，不给「稳胆」「必红」。Valve 客户端里的 Predictions / Fantasy 才是合法对照物。

现在最大的坑：队名与身份漂移

本届 H2H 如果按队名硬匹配会全错：PARIVISION → TEAM VISION，BetBoom → BoomBoys，Tundra → 1w → Iron Wing。正确主键是 team_id + 选手五人组，而不是牌子。否则「历史战绩」这一栏会直接骗人。

2. 产品长什么样

一个站点，三个使用节奏：赛前看预览、赛中看 BP 对照、赛后看模型校准。

01

总览 / 对阵图

双败图、下一场倒计时、瑞士成绩与晋级路径。点一场进入系列页。

02

系列预览页

每场核心页。H2H、阵容、近期状态、签名英雄、模拟 BP、系列胜率、竞猜建议。

03

队伍 / 选手页

本届 BP 画像、位置英雄池、一三楼倾向、对线英雄、LAN vs 线上差异。

04

版本 Meta 层

7.41e 职业优先度、本届 TI 禁用率、和「这支队会不会拿」分开显示。

05

竞猜面板

系列胜者、地图分、让分是否覆盖、信心低的场次明确标「过」。可导出当日卡片。

06

赛后复盘

真实 BP vs 模拟 BP、预测 vs 结果、校准曲线。没有这一页，模型会一直自我感觉良好。

3. 数据接口：液体百科能不能用？

能用，而且必须用——但它只覆盖「赛程事实」，覆盖不了「怎么打」。完整产品要叠四层数据。

L1 赛程事实

Liquipedia（液体百科）

  • 对阵图、开赛时间、阵容、转会、队名变更、VOD
  • 本届页面：The International/2026
  • Steam leagueid 已写在 infobox 里：19719

官方 REST v3（api.liquipedia.net/api/v3）要申请 API Key，结构化最好。没有 Key 时，MediaWiki action=parse 可以拉 wikitext，但必须带 Gzip 和合规 User-Agent，否则直接 406。

L2 比赛细节 · 已打通

OpenDota

  • 免费 REST，无需 Key 即可读公开职业数据
  • /leagues/19719/matches：本届已入库 100+ 场
  • /teams/{id}/heroes、/players/{id}/heroes：英雄池
  • /explorer：SQL 聚合 H2H、BP、时长、经济差

这是第一期主力。队名会空，必须用 team_id。八强 ID 已核对：VISION 9572001、Liquid 2163、NGX 10136357、Spirit 7119388、Iron Wing 10150413、Falcons 9247354、BoomBoys 8255888、Yandex 9823272。

L3 深度解析

STRATZ GraphQL

  • Replay 级：分路、视野、物品时序、Draft 顺序
  • 适合 BP 模拟和「赛况怎么打崩」
  • 需要 API Token，且有 Cloudflare 门

第二期再接。没有它，BP 模拟只能用「谁常拿 / 谁常禁 / 版本优先度」，做不到真实先后手建模。

L4 版本优先度

Dota2ProTracker + Steam

  • D2PT：7.41e 高分/职业英雄梯队，无稳定官方 API
  • Steam Web API：GetLiveLeagueGames 可做赛中刷新
  • Dotabuff / DLTV：补充，但爬虫脆弱，不作为主源

Meta 层第一期用 OpenDota /heroStats 的职业 pick/ban/win，D2PT 只作人工对照，不爬。

5. 分析引擎怎么做（你点的那几项）

  1. 历史战绩

    三层：同五人组最近 6 个月 H2H → 同组织近 12 个月（改名合并）→ 本届瑞士对共同对手。LAN 权重大于线上。样本小于 4 场就显示「不足」，不强行百分比。

  2. 常用英雄

    按位置输出：本届 TI 出场、7.41e 职业场、签名英雄（选手 career 高出场）。同时列「对方一禁名单」——这比胜率榜更接近真实 BP。

  3. 赛前模拟 BP

    第一期不做神经网络。用规则 + 蒙特卡洛：版本优先度 × 队伍英雄池 × 对手克制 × 先后手。跑 200 次草稿，输出「高概率 Ban」「一楼争抢」「可能的五保一/四核节奏」。第二期有 STRATZ 后再拟合真实 draft 顺序。

  4. 胜率

    先出赛前系列胜率（Elo + 近期状态 + LAN + H2H 小样本收缩），再出BP 后单图胜率。Bo3 用独立图近似，再校正「先胜方会不会换套路」。给区间，不给 51.2% 这种假精确。

  5. 赛况模拟

    不是录像生成。是三条路径：对线优势型、中期打架型、超长发育型——各给触发条件和谁更擅长。对照本届已出现的超长时长（本届平均时长偏高），明确标「这队怕拖 / 这队就吃拖」。

  6. 竞猜指导

    每场固定四格：系列倾向、地图分主推、是否覆盖让分、信心（高/中/低）。信心低就写「过」。全程标注这是模型意见，不是内幕，也不是投注建议。

6. 部署形态

推荐架构

静态前端（这个目录就能先挂 GitHub Pages / Cloudflare Pages）+ 一个很薄的数据刷新脚本。TI 这四天用定时拉取 OpenDota + Liquipedia parse，写成 JSON，前端只读本地数据。这样你打开的是网页，不是 Cursor。

为什么第一期不上重后端

淘汰赛一共就十几场系列。数据量小，缓存 JSON 足够。等 STRATZ Token、Liquipedia v3 Key 齐了，再加 API 层也不迟。先保证 8/20 能看四场预览。

Liquipedia parse / OpenDota REST
        ↓  定时脚本（每 15–30 分钟）
     data/*.json  （对阵、H2H、英雄池、模型输出）
        ↓
   静态网页  ← 你每天打开的就是这个
